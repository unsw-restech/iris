Nuclei Segmentation (U-Net)

Label every image in a set of fluorescence microscopy images as background, nucleus or nucleus edge. IRIS trains a 2D U-Net on your training pairs and segments each image. Each run is recorded, so you can view the labels over the images and compare runs with different settings side by side.

Demonstration workflow. This workflow shows what IRIS can do for KGLMF, the Katharina Gaus Light Microscopy Facility. It is a demonstration on public data that did not come from KGLMF, and it has not been validated on the lab's images.

Workflow owner: Patrick Tung · patrick.tung@unsw.edu.au

IRIS reviewed this workflow for safety and fit, not for its science: its workflow owner answers for its method and its results, so ask them about either.

Viewing and comparing runs

The data it needs

One dataset folder holding an image set and its training pairs, not a volume. You can arrange your own images this way, on your own computer:

  • images/ holds the image set, the images to segment, read in file-name order.
  • train/images/ holds the training images.
  • train/labels/ holds one label slice per training image, with the same file name and size: 0 is unlabelled, then 1, 2, 3 and so on per class. The number of classes is read from your labels, up to 255. Pixels left at 0 are ignored, so you can label just part of an image.
  • Every image and label slice is a single-page, single-channel 2D TIFF. Training images and the image set share one size and one bit depth.
  • IRIS adds a runs/ folder the first time you run on the dataset, with one folder per run.

The form checks this layout before it submits, and that every file in these three folders is a TIFF. Copy the folder to anywhere in your scratch as in Sending a dataset to Katana.

The prepared dataset is built from BBBC039, a public collection of fluorescence images of U2OS nuclei. Its 100 training fields become the training pairs and its 50 test fields the image set, so the images segmented are ones the model did not train on. Its label slices hold 1 for background, 2 for nucleus and 3 for nucleus edge. BBBC039's recommended citation is:

We used image set BBBC039v1 Caicedo et al. 2018, available from the Broad Bioimage Benchmark Collection [Ljosa et al., Nature Methods, 2012].

Editing the workflow code for one run

The form's script pane holds this workflow's code, run.py, below the comment # Edit the workflow code below. To try a different model architecture, loss, augmentation or training loop, edit it there before you submit: the job runs the code exactly as it appears in the pane. The change belongs to that run alone, which makes it an edited run; the workflow itself is unchanged. Record keeping and reading and writing images stay in IRIS, out of the pane, and an edited run uses the same Python packages.

  • Change the fields whenever you like. A field change rewrites only the lines that hold that field, so your edits to the code are kept.
  • Only the workflow code can be edited. The rest of the pane is shaded and locked: the #PBS lines at its top, the python line at its bottom and every other line the form writes. Hover over a locked line to see the field that sets it, or Fixed by the form, and click a field's line to go to that field.
  • To rerun an edited run, open History, click the Script Name in its row, then Load parameters: it restores the fields and your edited code, and the job output says the run is edited.
  • Every run directory keeps the code its run ran as run.py, and your changes as run.diff. The job writes both and prints the diff near the top of its output before the code starts, so a run whose code crashes, even one Python cannot read, still shows them. In the rare case the job cannot tell which commit the form showed, it warns, writes no run.diff, and run.json records that whether the run is edited is unknown.
What a run writes and how to view it

Each run writes a run directory into your dataset, runs/<job number>/:

FileWhat it holds
labels.tifThe labels: one uint8 page per image, in file-name order, each pixel holding its class number
model.ptThe trained weights
params.jsonEvery form field, and the seed used
metrics.jsonTraining loss and per-class Dice and IoU, per epoch and final
dataset.jsonWhat the run read: the dataset folder's path, file count, total size and newest change, then under extras the image set's shape, type and intensity statistics, the file name of each page of labels.tif in order, and how many training pairs it read
run.jsonThe experiment, job ID, how the run ended and whether it is an edited run
commit.txtThe IRIS commit that ran, as the form showed it
run.pyThe workflow code the run ran, as submitted from the form
run.diffYour changes to that code against the commit in commit.txt; empty unless the run is edited, and missing if the job could not tell which commit the form showed
lib_commit.txtOnly if IRIS was updated between opening the form and the job starting: the commit of the IRIS code outside the pane that the run used

The job output sits beside it, as runs/<job ID>.OU. When the job succeeds, the output ends with the commands to run in a terminal in a Virtual Desktop: module load iris, then iris-view with the run directory, which shows the labels over your images in napari, with a slider to step through every image, and iris-compare, which opens your runs in MLflow. The guide covers the Virtual Desktop to start, both commands, and copying a run directory home.

To cite a run, use the commit in its commit.txt, as in Cite this workflow.

Something went wrong
  • The form won't submit. Its warning names the rule your dataset folder broke, and your values are kept. Fix the folder and submit again. A stray .DS_Store or Thumbs.db in one of the train/ folders counts as a file-name mismatch, and one in images/ as a file that isn't a TIFF: delete it.
  • The job stopped at once with "the IRIS imaging environment is missing". Nothing is wrong with your data. Email the workflow owner with the job ID.
  • The job stopped before training with an ERROR: line about your dataset. It names the file and what's wrong: a file that isn't a single-page, single-channel 2D TIFF, an image at a different size or bit depth from the others, a label slice that doesn't match its image, label values that aren't whole numbers from 0, more than 255 classes, or labels that are all 0.
  • The job ran out of walltime. Submit again with more walltime. Load parameters in History keeps your other settings.
  • The job ran out of GPU memory. Lower the batch size under advanced options, or the patch size.
  • iris-view says there is no label volume. The run hasn't finished, or it failed: read the end of its runs/<job ID>.OU.
  • iris-view says images/ no longer holds the images this run labelled. An image has been added to the image set, removed or renamed since the run, so the labels would show over the wrong images. Put the image set back as the run read it: dataset.json in the run directory lists its file names.
  • The job output doesn't end with the iris-view line. The job stopped at its first error, which is the last thing in the output. The same commands are printed near the start of the output, so the run directory they name may be incomplete.
  • Anything else. Email the workflow owner with the job ID and the end of the job output.
